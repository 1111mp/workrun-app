title: 运行、调试与追踪
description: 用运行记录建立证据链：定位失败节点、检查输入与副作用，再安全地恢复或修复自动化。
---

一次运行不只有「成功」或「失败」。Workrun 会在运行工作区保留工作流快照、状态变化、节点事件、模型与工具活动、Python 日志和运行诊断。用它回答一个具体问题：**这次运行在哪一步、基于什么输入、以什么结果停下，以及下一步该改什么？**

不要从最终回答倒推原因。先建立证据链，再改 Prompt、代码、Schema、权限或模型配置。

## 失败后，先用这五步收窄范围

1. 在运行历史中打开这一次运行，确认工作流版本、运行输入与开始时间；不要和另一版工作流或另一条对话混在一起。
2. 看节点时间线，找到最后一个不是「已完成」的节点。它是排查起点，不一定是根因。
3. 查看该节点前后事件，确认上游是否真的发布了它需要的状态，以及它是否有读取权限。
4. 按节点类型查看证据：Agent 看模型消息与工具活动；Process App 看 stdout、stderr 与结构化结果；条件节点看字段值与走出的分支。
5. 确认外部副作用后再恢复或重试。修复后用同一组输入重新运行，并把可复现的问题加入评测集。

这套顺序把「发生了什么」和「该怎么修」分开：先确定事实，再选择改动位置。

在单个工作流中，运行历史同时展示一段时间内的健康度和每次执行的状态、耗时与 Token。先从这里选择需要调查的那一次，再点击「查看输出」进入运行工作区。

## 先看运行状态，决定是否应该操作

| 状态                        | 它表示什么                             | 下一步                                                               |
| --------------------------- | -------------------------------------- | -------------------------------------------------------------------- |
| `queued` / `running`        | 已排队或仍在执行。                     | 等待新事件；若长期没有新事件，再检查当前模型或工具的超时。           |
| `waiting_for_input`         | 正在等待人工审核、提问回答或工具确认。 | 在运行面板完成该操作；不要把它当作失败重新运行。                     |
| `completed`                 | 本次执行已结束。                       | 核对最终状态与诊断；结果异常时，从产生错误值的节点向上追溯。         |
| `failed`                    | 某个节点或运行时步骤未完成。           | 先读错误、事件和节点证据；确认没有重复副作用后才考虑检查点重试。     |
| `cancelled` / `interrupted` | 人工取消，或应用在执行中断开。         | 不假设执行没有影响；检查最后事件和外部系统，再决定新开运行还是调查。 |

> 等待输入是可恢复的暂停；失败重试会创建新的运行分支，并从可用检查点继续。两者不是同一个动作。

![全局运行历史：可按工作流或应用、任务或对话模式，以及排队中、运行中、需要处理、失败等状态筛选已保存的执行记录。](/media/runs/02-all-run-history.png)

全局「运行历史」会汇总工作流与 App 的本地执行记录。遇到不确定运行来自哪里、或需要查找被中断和失败的 App 运行时，先用名称、目标类型、模式和状态筛选，再打开对应输出。

## 运行工作区：每种证据回答什么

| 证据                        | 先问的问题                                       | 常见结论                                             |
| --------------------------- | ------------------------------------------------ | ---------------------------------------------------- |
| 节点时间线与事件            | 卡在哪个节点？完成、等待、失败的顺序是什么？     | 问题属于 Agent、App、工具、条件或人工操作哪一层。    |
| 运行输入与上游状态          | 键、类型和值对吗？上游发布了所需字段吗？         | 缺少必填值、键名不一致，或下游没有读取授权。         |
| 模型消息与结构化输出        | Agent 实际看到了什么？输出符合契约吗？           | Prompt、模型、Schema 或状态边界需要调整。            |
| 工具活动                    | 参数、审批、调用上限与返回结构正确吗？           | 工具描述、状态绑定、权限或服务需要修复。             |
| Process App stdout / stderr | Python 在哪里失败？返回了预期 JSON 吗？          | 依赖、环境、业务逻辑或 App 数据契约有问题。          |
| 最终状态                    | 哪些字段真正交付给输出和下游？                   | 值没有发布、被覆盖，或敏感数据可见范围需要重新设计。 |
| 运行诊断                    | 哪个节点、模型或工具消耗时间、Token 或调用次数？ | 限制工具调用、缩短上下文、换模型或定位性能瓶颈。     |

运行记录会保存这次目标的快照、最终状态和事件序列。先固定这份证据，再修改当前草稿；否则很难确认修改是否解决了同一个问题。

![工作流运行输出中的最终状态：全局状态显示已发布的键，节点状态保留各节点的私有输出，便于核对哪些值真正交付给下游。](/media/runs/03-workflow-final-state.png)

先查看全局状态，确认工作流输出与下游依赖的键是否存在；再展开节点状态，追溯具体值由哪个节点产生。图中的消息与工单编号仅为演示数据，真实运行应依照状态访问和脱敏规则处理敏感字段。

## 按节点类型排查

### Agent：先看输入，再看决定

依次确认：

1. Agent 使用了已配置的模型，模型消息中确实有它需要的输入；
2. 指令明确了工具的使用条件、输出格式和不能做的事；
3. 结构化输出符合 Schema，且后续节点所需字段已发布；
4. 结果不稳定时，用相同输入多跑几次，再决定改 Prompt、模型还是验收规则。

不要只因最终自然语言看起来合理就结束排查。条件和下游节点应依赖稳定的结构化字段，而不是从一段回复里猜测值。

### Tool App、MCP 与远程工具：检查调用边界

工具没有被调用时，确认它已在该 Agent 的工具列表中启用，且名称、描述和 Agent 指令说明了调用条件。调用失败时按顺序检查：

1. 参数是否来自正确的已授权状态键；只有参数名与状态键不同时才需要状态绑定；
2. 是否正在等待人工确认，或已达到调用上限、单次超时；
3. 返回值是否符合声明的 Schema，而不只看服务端是否返回 HTTP 成功；
4. 对 Tool App，再检查它自己的 stdout 和 stderr。

对发送、写入、删除等副作用工具，先在外部系统确认操作是否已经发生，再决定是否重试。

### Process App：把日志和返回值分开看

Process App 的 stdout 和 stderr 用于调试；`process.result({...})` 才是交给工作流的结构化结果。分别确认：代码是否执行、依赖与环境是否可用、返回对象是否符合 App 契约、下游所需输出键是否已在节点中发布。

如果 App 独立运行正常、进入工作流后失败，优先检查工作流状态输入、读取授权和已发布输出键，而不是立刻修改 Python 代码。详见[使用 Python App](/zh-cn/guides/python-apps/)。

### 条件、状态与人工节点：检查可见数据，不要猜路由

条件节点应读取明确发布的稳定字段。分支不对时，检查产生该字段的节点输出、它是否已发布、条件表达式读取的键，以及实际命中的出口。人工审核或提问暂停时，运行会保留检查点；完成操作后从原处继续，已完成节点不会重新执行。

完整的状态边界、脱敏和检查点模型见[工作流与状态](/zh-cn/concepts/workflows-and-state/)。

## App 补偿后，修复并重新运行

workflow 失败时，配置了补偿入口的成功 App 调用会自动清理，包括 Agent 内部成功的 Tool App 调用。先查看对应节点 message 的补偿状态，并核实未完成或结果未知的资源。补偿启动后，不再从检查点继续使用已清理的结果；修复后点击“重新运行”，创建新任务执行一轮新的业务，原运行保留失败与补偿证据。

停止执行不触发自动补偿，正常完成也不会清理。配置教程与异常处理见[App 失败补偿](/zh-cn/guides/app-compensation/)。

## 从检查点恢复前，先确认副作用

以下检查点操作仅适用于尚未启动自动补偿、且界面允许继续的运行。已启动 App 补偿的任务请使用“重新运行”。

失败运行可以从最新检查点创建新的重试运行。此前已完成节点不会再次执行，但失败节点在报错前**可能已经**发送消息、写入记录或调用外部服务。重试前应：

1. 在运行事件和外部系统中确认失败节点执行到了哪里；
2. 对写入类操作检查幂等键、去重逻辑或可安全重复的业务规则；
3. 修正凭据、参数、代码或配置后，再选择「从检查点重试失败节点」；
4. 如果无法证明副作用状态，保留这次运行作为证据，并以受控的新输入启动新运行。

检查点重试目前要求检查点中只有一个待执行工作流节点。并行分支失败时，先用运行历史判断应恢复哪个分支，必要时启动新的运行。

## 用运行诊断找到慢和贵的地方

![运行输出中的运行诊断：逐项列出工作流节点、模型调用与工具调用的状态、Token 使用量和耗时。](/media/runs/04-runtime-diagnostics.png)

诊断会把同一节点下的工作流节点事件、模型调用和工具调用分开列出。例如可对比 Agent 的模型用量与 `lookup_order` 的工具耗时，判断瓶颈在模型、工具还是 Process App。

「运行诊断」会汇总工作流节点、工具调用和模型调用的耗时与状态；当 Provider 返回用量时，还会显示输入、输出和总 Token，以及估算成本。用它判断：模型调用是否变慢、工具是否持续超时、调用次数是否过多，以及 Token 增长来自上下文、输出还是推理。

单次异常先回到事件和输入；重复模式再用评测集或版本对比验证。有关批量回归验证与发布质量门，参见[评估与质量门](/zh-cn/quality/evaluations/)。

## 将 Trace 接入现有观测系统

运行工作区始终是单次执行的第一手证据。需要把 Workrun 与其他服务联查时，可在 **设置 → 日志** 中填写 OTLP/gRPC collector endpoint；保存新地址后需要重启应用才会生效。

配置前请确认 collector 地址与网络策略只允许预期接收方、Trace 不包含不应离开设备的敏感内容或凭据，并先在隔离环境用非敏感运行验证连接、字段和保留策略。

OTLP 是诊断导出，不替代本地运行记录、状态边界或逐次结果检查。

Workrun 是本地优先的 AI 自动化工作台。它解决的不只是「如何再问一次模型」，而是如何将一次有效的 AI 协作做成团队能够重复运行、检查和改进的工作流。

```text
运行输入
   ↓
工作流状态 ──→ Agent / Python App / MCP 与 Tool App / 人工决策
   ↓                                  ↓
最终结果 ←──── 显式发布的状态、节点事件和工具结果
   ↓
运行历史、检查点、追踪、评测与可发布版本
```

## 一个工作流由什么组成

工作流是一份可保存的画布定义：节点决定谁执行工作，连线决定下一步去向，**更多设置 → 运行输入** 定义每次运行可以传入的值。新工作流自带一个不可编辑的 `Start`；它是唯一的固定入口，而不是配置输入的地方。

运行前，Workrun 会检查图结构和路由是否有效，例如必须只有一个 Start、Start 必须连接到可执行节点、分支连接必须与节点的分支出口相匹配。通过检查后，桌面端将画布编译为执行图，再以本次运行的输入初始化状态。

常用节点及其职责如下：

| 节点 | 职责 |
| --- | --- |
| `Agent` | 用所选内置模型、指令和可选工具处理需要推理的任务。 |
| `CodeAct Agent` | 让模型在受控的 Python 执行环境中组合代码与工具，并可限制迭代、工具调用、时长、内存、挂载目录和环境变量。 |
| `Process` | 运行一个本地 Python App，适合确定性规则、数据处理和系统集成。 |
| `If/Else`、`Switch` | 根据状态中的条件选择后续路径。 |
| `Human Review`、`Ask User Question` | 暂停运行，等待人工审核或用户选择后继续。 |
| `Subworkflow` | 调用已保存的工作流，将复杂流程拆成可组合单元。 |
| `Remote Agent` | 通过 A2A 调用远程 Agent。 |
| `Terminate`、`End` | 结束当前流程；`Terminate` 可终止整次工作流执行。 |
| `Group` | 仅用于画布布局，不参与执行。 |

## 状态是显式的，而不是隐式上下文

每次运行都有自己的状态。输入字段会成为初始状态；节点产生的数据默认留在自己的命名空间，只有显式发布的字段才能成为后续节点可用的全局状态。节点还需要被授予相应的读取权限。

这种边界让工作流更容易审查：你可以看清某个 Agent、App 或分支读取了什么、产出了什么，而不是让任意步骤静默修改全部上下文。工作流输入和输出可定义为字段 Schema；Agent 也可配置结构化输出或结果键，为后续条件和节点提供稳定的数据形状。

```text
运行输入 → 状态
             ├─ Agent：读取获授权字段，生成结果
             ├─ Process：处理状态并返回结构化更新
             └─ 条件节点：读取已发布字段并选择路径
```

更多细节见[工作流与状态](/zh-cn/concepts/workflows-and-state/)。

## 为推理、代码与工具分配正确的工作

Workrun 不要求把所有事情塞进提示词。不同执行方式的边界是刻意设计的：

- **Agent**：适用于总结、分类、计划、提取、解释和需要语义判断的任务。它使用节点指令、所选模型与已获授权的状态，并可调用工具。
- **Process App**：适用于可预测的 Python 逻辑、文件/数据处理和系统集成。每个 App 是一个可编辑的本地 `uv` 项目，拥有自己的 `pyproject.toml`、锁文件、虚拟环境和入口脚本。
- **Tool App 与 MCP 工具**：适用于让 Agent 按 Schema 查询、计算或执行操作。Tool App 是本地 Python 工具；MCP 可连接本地 `stdio` 或远程 Streamable HTTP Server，并支持无认证、Bearer Token 或 OAuth。
- **Skill**：为 Agent 提供可渐进加载的任务说明和受限工具集合，避免每次都把所有上下文与工具暴露给模型。
- **人工节点**：适用于高风险决策、需要确认的工具调用，或模型无法自行补全的信息。

本地 Python App 不是沙箱。只运行你信任的项目，并按实际权限范围审查它们。参见[App、工具与 MCP](/zh-cn/concepts/apps-tools-and-mcp/)。

## 运行、暂停与恢复

Workrun 将一次执行视为有身份的运行，而不是一次不可追溯的聊天请求。运行过程中，界面会持续显示节点开始、完成、失败或等待输入等事件；Agent 的模型消息、工具调用、Python 日志和关键输出也可在运行面板中查看。

当流程到达 Human Review 或 Ask User Question 时，会写入本地 SQLite 检查点并进入等待状态。提交审核结果或选项后，Workrun 从暂停点继续，不会重新执行之前已完成的步骤。失败的后台运行也可以从检查点重试；当前重试要求检查点只剩一个待执行节点，因此并行分叉的失败需先查看运行记录再处理。

任务工作流适合独立的一次性运行；对话工作流会保存会话及其多轮记录，允许后续消息延续同一上下文。

## 安全边界与可观察性

凭据在本机加密保存。工作流输入和节点输出可以标记为敏感：原始状态以加密形式保存在检查点中，而提供给模型、工具和界面的默认视图会进行脱敏。Workrun 也会对常见的 PII 和凭据模式执行输入、输出及工具参数护栏，降低敏感信息进入工具调用与运行证据的风险。

每次运行保留工作流快照、最终状态和关键事件。运行面板用于定位问题发生在哪个节点；需要接入外部可观测性时，可配置 OTLP/gRPC collector 导出诊断 Trace。详情见[运行、调试与追踪](/zh-cn/quality/runs-and-traces/)。

## 从试验到可交付能力

Workrun 把「能跑」与「值得发布」分开：

1. 用真实输入搭建并运行工作流；
2. 在运行历史中检查结果、工具调用和错误；
3. 为 Agent 工作流建立评测集，使用断言和工具模拟结果做回归检查；
4. 在团队工作区发布版本，并可用质量门约束发布。

评测执行目前面向仅含 Agent 节点的工作流；包含 Process、CodeAct Agent、Remote Agent、人工节点或子工作流的流程，应以正常运行和运行历史验证。团队发布会固定引用的团队 App 版本，使后续运行和历史结果能够关联到对应版本。

Workrun 的核心价值因此不在于替代模型或代码，而在于为它们提供一套明确的编排、状态、安全、恢复和验证机制。

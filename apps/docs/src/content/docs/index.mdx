## From one Python App to automation your team can deliver.

Workrun is not only a workflow canvas. Start with an independent local Python project that does one concrete job, or compose Agents, Apps, MCP tools, and human judgment on a canvas into a repeatable process. Both paths use the same workspace for running, debugging, evaluating, and publishing.

## An App is more than a node: run it independently first

For data processing, file operations, internal integrations, or a local tool that needs input from a person, an App can run directly from **Apps**. Workrun creates and runs the project, preserves run history, and handles runtime interactions; the Python remains your codebase.

## When one App is not enough, compose it in a Workflow

Workflow configuration should not be a black box. It should remain visible and inspectable: where a node reads data, who makes a decision, when a human takes over, and which model and tools a run used.

## Whichever path you start with, evolve in one workspace

| What you need to do | How Workrun helps |
| --- | --- |
| Compose capabilities | Run an App independently, or connect Agents, Processes, branches, subworkflows, and human nodes on a canvas. |
| Run reliably | Isolated node state plus checkpoint recovery for pauses, failures, and background runs. |
| See what happened | Inspect model messages, tool calls, script logs, and traces node by node. |
| Iterate safely | Validate workflow changes with evaluation suites and quality gates before publishing. |
